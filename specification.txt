# Name
 - Monolisp.ts

# Techstack
 - SBCL, TSC, React

# Summary 
 - Monolithic full-stack application server written in Common Lisp
    - Can be deployed as a serverless full-stack application server due to edge/server function architecture
 - Transpiler for turning frontend Lisp code into browser frontend Typescript/Typescript XML

# Details
 - Backend is written in pure Common Lisp
    - Backend is defined as a collection of "server functions", which can be deployed as edge functions
       - Compiled into JSON-RPC2 function endpoints
       - Must be intentionally declared in a salient way to indicate to developer that these will be exposed publically as frontend-accessible endpoints
       - Frontend transpiler will type-check the frontend calls to server functions to ensure that the types passed in the frontend call match the type specifications set on the backend server functions
       - Pay special security attention to the client-server JSON-RPC2 endpoint boundary
          - This (de)serialization layer is one of the common points of vulernability in this kind of architecture
          - Since user input and unauthenticated internet data will be focused on this layer:
             - It need to be aggressively defended and sanitized
             - All data being processed by this layer should be assumed to be from a potential hacker
                - Every single byte of the JSON-RPC2 payload needs to be considered, from the function name, to the function ids to the padding characters could be a possible attack vector
    - Base webserver will be a custom `cl-async` (libuv) based JSON-RPC2 endpoint only webserver
       - Must support async network IO and async IO in general by leverging either cl-async or libuv calls
       - For example:
          - Must be able to make asynchronous fetching calls to slow backend APIs without hogging a webserver connection
          - An asynchronous macro system to organize asynchronous chains to prevent callback hell
             - Try to extend cl-async as much as possible, or roll own library if cl-async is not flexible enough or high performance enough
             - Put all async supporting code in a clear and defined sub-directory for possible splitting into a separate project
 - Frontend is written in a Common Lisp dialect
 - Frontend invokes the backend through normal looking Common Lisp function calls
    - Transpiled into browser frontend Typescript
    - Syntax will mirror browser frontend Typescript (will incorporate many non-ANSI Common Lisp functions)
       - `async` and `await` from JS/TS will be special functions that behave identically to their JS/TS counterparts
       - However, JS/TS `for` and `while` loops will not exist
          - Common Lisp `loop` macro will be fully supported as the transpiler should be able to translate the control flow primitives generated by the expanded `loop` macro into efficient TS equivalents
    - `declare` and `declaim` will be used to provide inlining and type declarations for the Lisp code
       - Transpiled into direct Typescript type specifiers
       - If the type declarations/declamations are missing for some variables/functions in the Lisp source code:
          - Transpile those as `any` type in Typescript
       - `optimize` declaration will not be supported
    - CLOS will not be supported
    - `defstruct` will transpile to type to TypeScript interfaces
       - Allow for limited inheritance via `defstruct`'s `:include` option (Typescript `extend`, but only for 1 other `defstruct`)
    - `lambda` will directly transpile into arrow functions
    - Macros will be fully supported
       - Expanded by the transpiler before actual transpiling into Typescript
    - Lisp lists and cons cells will **not** exist or be supported on the frontend
       - Implementing a falsy empty list is too complex
       - Instead, the frontend developer should use Common Lisp arrays wherever they expect to use JS/TS arrays
       - `dolist`, `dotimes` and `doarray` do not exist; iteration over arrays is `for-each` (side effects, returns nothing) and `map` (builds and returns a new array), both with the binding syntax `(for-each (x xs [i]) ...)` / `(map (x xs [i]) ...)`
    - All frontend Lisp arrays (i.e. made by `make-array`) will have adjustable length by default
       - The `:adjustable t` option for `make-array` will not exist
       - Manipulating the array's fill-pointer will translate to manipulating the `.length` field of a JS/TS array
    - Frontend Lisp will have a `concat` function instead of Common Lisp's `(concatenate 'string ...)`
       - Can accept any number of strings as arguments
    - Frontend Lisp will support multiple value binding and returning
       - `values` built-in function will provide multi-value returning
       - Multiple value binding will be done through the `let` form via a `:multi` indicator (can be combined with `:const`)
          - Example:
```lisp
(let ((something "hi")
      (:const :multi (state set-state) (useState ""))
      (:multi (things other-things something-else) (function-that-returns-multiple-values)))
  ...)
```
```typescript
let something = "hi"
const [state, setState] = useState("")
let [things, otherThings, somethingElse] = functionThatReturnsMultipleValues()
```
    - Each .client[x].lisp file is an ESM module that can be imported from other frontend Lisp files
    - JS object literals are specified as Common Lisp plists with a `'{}` prefix
    - `progn` will be transpiled to `{}` block scopes
    - `handler-case` will be transpiled to `try{...}catch{...}` blocks
    - `case` will be transpiled to `switch...case...default` blocks
       - Use `otherwise` as the default branch specifier
    - JS/TS syntax to frontend Lisp guide:
       - JS/TS spread operator `...` -> frontend Lisp `spread` built-in function
       - JS/TS ESM `import` keyword -> frontend Lisp `import` built-in macro (file name must be the target module basename, no file extensions)
          - Examples: 
             - `(import :from "three" :targets :all :as THREE)` -> `import * as THREE from "three"`
             - `(import :from "three" :targets (WebGLRenderer (:type Vector3Like Intersection) MathUtils Color (:type Material)))` -> `import { WebGlRenderer, type Vector3Like, type Intersection, MathUtils, Color, type Material } from "three"`
             - `(import :from "react" :targets React)` -> `import React from "react"`
       - JS/TS ESM `export` keyword -> frontend Lisp `export` built-in macro (can only target `defvars` and `defun` forms)
          - Examples:
             - `(export (defvar hello-world "hiii"))` -> `export var helloWorld = "hiii"`
             - `(export (defun do-thing () ...))` -> `export function doThing() {...}`
       - JS/TS ESM `export default` keywords -> frontend Lisp `export-default` built-in macro (can only target `defvars` and `defun` forms)
          - Example:
             - `(export-default (defun do-thing () ...))` -> `export default function doThing() {...}`
       - Global variable JS/TS `var` keyword -> frontend Lisp `defvar` built-in function
       - New object instance JS/TS `new` keyword -> frontend Lisp `new` built-in function
       - JS/TS nullish coalescing operator `??` -> frontend Lisp `nil-or` built-in function (can accept multiple args to replicate repeated `??` chaining)
       - JS/TS dot chaining function call `<variable>.<variable-2>.<function>(<arg-1>, <arg-2>)` -> frontend Lisp `(.. <variable> <variable-2> (<function> <arg-1> <arg-2>))` built-in macro (ensure that the variable args before the last arg are only evaluated once)
          - Examples:
             - `(.. React (createElement "h1" '{}(:className "hello-message") "HIII"))` -> `React.createElement("h1", { className: "hello-message" }, "HIII")`
             - `(.. Something (do-something))` -> `Something.doSomething()`
       - JS/TS dot chaining variable access `<variable>.<variable-2>.<variable-3>` -> frontend Lisp `(.. <variable> <variable-2> <variable-3>)` built-in macro (ensure that the variable args before the last arg are only evaluated once)
          - Examples:
             - `(.. React Fragment)` -> `React.Fragment`
       - JS/TS null safe dot chaining access `<variable>?.<variable-2>?.<variable-3>` -> frontend Lisp `(.. <variable> (:? <variable-2>) (:? <variable-3>))` (only usable inside of `..` built-in macro)
          - Examples:
             - `(.. data (:? user) (:? preferences) (:? theme) (:? color))` -> `data?.user?.preferences?.theme?.color`
       - JS/TS `let` and `const` keywords -> frontend Lisp Common Lisp `let` form but with `:const` keyword optionally before a variable symbol to signify that it will be `const`
          - Example:
```lisp
(let ((thingy "hi")
      (something "um")
      (:const else "world"))
  ...)
```
```typescript
let thingy = "hi";
let something = "um";
const something = "world";
```
       - JS/TS `=` setting operator -> frontend Lisp `setf` built-in macro
          - Examples:
             - `(setf my-existing-variable 67)` -> `myExistingVariable = 67`
    - Many commonly used JS/TS functions will be aliased to inline shorthands to avoid `..` overuse
       - Examples:
```lisp
;; something like this is declared in an internal definer file
(declaim (inline console-log doc-create-element doc-body-append-child append-child add-event-listener for-each stringify-json slice doc-get-element-by-id doc-query-selector-all))

...

(console-log "hi") ;; console.log("hi")
(doc-create-element "img") ;; document.createElement("img")
(doc-body-append-child <element>) ;; document.body.appendChild(<element>)
(doc-get-element-by-id "my-id") ;; document.getElementById("my-id")
(doc-query-selector-all "my-class") ;; document.querySelectorAll("my-class")
(append-child <element> <element-2>) ;; <element>.appendChild(<element-2>)
(add-event-listener <element> "click" (lambda (e) (alert "hi"))) ;; <element>.addEventListener("click", (e) => alert("hi"))
(for-each (e <array>)  ;; <array>.forEach((e) => {console.log(e); console.log("hi")})
  (console-log e)
  (console-log "hi"))
(stringify-json '{}(:something "hi" :else "world")) ;; JSON.stringify({something: "hi", else: "world"})
(slice <array> 6 7) ;; <array>.slice(6, 7)

```
    - Type declarations will be limited to only Typescript equivalent types
       - `nil` -> `null`
       - `:undefined` -> `undefined`
       - `:true` -> `true`
       - `:false` -> `false`
       - `SYMBOL` -> `string`
       - `KEYWORD` -> `string` (but always prepended with a ":")
       - `CHARACTER` -> `string`
       - `STRING` -> `string`
       - `NUMBER` -> `number | bigint`
       - `FLOAT` -> `number`
       - `FIXNUM` -> `number`
       - `BIGNUM` -> `bigint`
       - `RATIO` -> `{ numerator: bigint; denominator: bigint }`
       - `COMPLEX` -> `{ real: number; imag: number }`
       - `ARRAY` -> `any[]`
       - `VECTOR` -> `any[]`
       - `BIT-VECTOR` -> `Uint8Array`
       - `HASH-TABLE` -> `Map<any, any>`
 - `eval` will not be supported on the frontend or backend
    - Set `*read-eval*` to `nil` on the backend
 - Backend files will have file extension .server.lisp
 - Frontend files will have file extension .client.lisp
    - Frontend files can also have file extension .clientx.lisp for Typescript XML (.tsx) compilation
       - Such files will support Spinneret style S-expession XML forms as objects
       - Example:
```lisp
(defun main-component (prop-1 prop-2 prop-3)
  (as-html-string
    (:div :style '{}(:backgroundColor "dodgerblue" :color "white" :transform "scale(2.0)" :border "1px solid #ccc"))
    (:div :class "test-class"
      (:h1 :id "big-header" "hi")
      (:p :class "body-text" "hello"))
    (:div :class "other-class"
      (:div :class "next-class"
        (map (cur-thing prop-1)
          (:p :key cur-thing (concat cur-thing prop-2)))))))
```
 - Configuration option to add React as the clientx backend
    - Doing so will auto import React into the .tsx files
 - Frontend is compatible with any NPM installed JS/TS library that is compatible with an equivalent frontend ESM module project
